# API та обмін — перевірка 1.3.34

Дата: 19.10.2026. Первинні перевірки виконано в ізольованих середовищах. Локальний Docker на порту 8085 перезапущено під час подальшого виправлення, описаного нижче.

## Поведінка

- `/teacher-portal/api/` показує підключення доступних журналів. `/journal/<id>/integrations/` відкриває той самий простий вигляд для одного журналу. Технічні поля та старі маршрути збережені в додаткових налаштуваннях.
- `/notifications/` і вкладка «Сповіщення» показують поточні питання: зв’язок, отримання оцінок, передача списків, клас і предмет, відповідності учнів, оцінки та збережені результати для перевірки. Лічильник у меню й картки журналу використовують ті самі дані.
- Для оцінок, списків і перевірки зв’язку береться останній результат кожної операції в межах підтвердженого сайту, журналу, класу та предмета. Повторний успіх відповідної операції прибирає повідомлення; історія викликів зберігається. Успішна передача списку не приховує невдалого отримання оцінок.
- Сповіщення веде до конкретної адреси та потрібного блоку. Блоки розгортаються, а збережена прокрутка не перебиває явний перехід до проблеми. Перегляд сторінок не викликає зовнішні API.
- «Резервна адреса» перевіряє ідентичність джерела, зберігає основну адресу та переносить контекст, відповідності й підтверджені ID списку. Запит API повторюється через наступну адресу також за відмови самого API. Імпорт оцінок виконується один раз після успішного отримання. Вимкнені адреси пропускаються.
- Інструкція для користувача: `/help/#api-start`; також доступна з розділу API та сторінки підключення.

Серверні регресії перевіряють ізоляцію шкіл і особистих nz.ua-профілів, відсутність ключів у HTML, збереження історії, незалежне вирішення помилок операцій, резервну адресу чужого сервісу, збій API після успішної перевірки порту, відсутність повторного імпорту та збереження канонічного ID учня з кількома псевдонімами.

Браузерні сценарії перевіряють справжні HTTP-сторінки та POST-маршрути, згортання технічних налаштувань, додавання підключення, показ двох адрес однією карткою, переходи до адреси й списку, інструкцію, відсутність горизонтального переповнення та помилок JavaScript. Успішна перевірка зв’язку прибирає лише її сповіщення; успішна повторна передача списку прибирає зауваження до списку.

Знімки з вигаданими даними збережені у `/tmp/schooljournal-api-workspace-artifacts/`. Порядок повторення браузерної перевірки наведений у `tests/ux/README.md`.

## Межі перевірки

Для наведених автоматичних тестів використовувалися тимчасові бази та вигадані користувачі. Робочий `.env`, бази, томи й онлайн-журнали в цих тестах не використовувалися. Відповіді зовнішніх джерел підмінені; фактична доступність конкретних IP-адрес, ключів користувача й робочих сайтів цими тестами не підтверджується. Нових міграцій немає.

## Уточнення: HTTP 500 у локальному Docker після входу

19.10.2026 користувач повідомив про HTTP 500 на `/teacher-portal/` після входу через nz.ua на `192.168.1.12:8085`.

У локальний контейнер змонтовано нові `apps`, `templates`, `static` та метадані випуску. Запущені Gunicorn-процеси зберігали попередній код і кеш маршрутів: `/healthz/` повідомляв версію 1.3.33 за змонтованого `VERSION` 1.3.34; `/help/` повертав 500, нові `/teacher-portal/api/` та `/notifications/` — 404. У свіжому Python-процесі обидва маршрути вже визначалися правильно. Це пояснює збій під час відображення нової навігації після входу.

Перед перезапуском перевірено `migrate --plan`: незастосованих міграцій немає, `manage.py check` без зауважень. Перезапущено лише `schooljournal-web-1`; база та інші сайти не перезапускалися. Після перезапуску через локальний Nginx отримано:

- `/healthz/`: 200, версія 1.3.34.
- `/help/`: 200.
- `/teacher-portal/`, `/teacher-portal/api/`, `/notifications/`: штатний 302 до входу для запиту без облікових даних.

До `compose.dev.yaml` додано Gunicorn `--reload` та відстеження метаданих версії; `docker compose -f compose.yaml -f compose.dev.yaml config --quiet` успішний. README пояснює перезапуск після змін коду поза цим режимом та після змін CSS/JavaScript. Повторний вхід у власній вкладці залишається перевіркою користувача; збережені cookies для HTTP-перевірки не використовувалися.
