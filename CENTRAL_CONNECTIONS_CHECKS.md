# Централізовані підключення — поетапні перевірки

## Етап 1 — моделі та міграція

Додано NetworkProfile, NetworkSelection, ServiceConnection та ServiceEndpoint.
GradeAPIConnection зберігає свій PK і роль прив'язки конкретного журналу.
Міграція 0020 об'єднує адреси лише в межах власника, джерела та підтвердженої
ідентичності / того самого ключа. Невідомі ручні групи збережені окремо,
незвичні старі URL залишені без перетворення. Вимкнені адреси не вмикаються.
Учні, відповідності, історія, уроки та оцінки не змінюються.

Ключі старих прив'язок та центральних підключень зберігаються через
Fernet + HKDF від приватного SECRET_KEY; SECRET_KEY_FALLBACKS підтримує
ротацію. Приватна копія конфігурації потрібна для відновлення ключів.
Повний ключ не показується навіть для коротких старих значень.

school_sync синхронізовано побайтно з двома джерелами: збережено перевірки
класу / UUID, ignored та захист тезок. Контракт schema_version=2 незмінний.

Перевірки на синтетичних даних: 637 тестів журналу успішно на SQLite,
11 остаточних цільових тестів міграції / ключів, включно з вимкненими
адресами, успішно. 26 спільних тестів пройшли в кожному
репозиторії. Перевірено справжній перехід зі схеми 0019 на 0020 та назад,
збереження PK, відповідностей і ручної оцінки. Схема відповідає моделям.

Ручна перевірка на тестовій копії: застосувати 0020, виконати старі дії
перевірки ключа / передачі списку; ID прив'язок і чинний ключ мають лишитися
тими самими. Для автоматизованої перевірки: `python manage.py test
tests.test_central_connections --settings=config.test_settings --noinput`.
Робоча база цим тестом не використовується. Інтерфейс профілів додається
на наступних етапах; цей коміт ще не є завершеним випуском функції.

## Етап 2 — перевірка і вибір мережі

Додано публічний `GET /api/v2/ping` з трьома полями source, instance_id,
version. Джерела також надають авторизований `/api/v2/journal/connection/`
з правами ключа; списків учнів у цих відповідях немає.

Перед обміном центральне підключення перевіряє source / UUID без токена,
обирає робочий endpoint і пам'ятає його. Строка прив'язки журналу й старий
URL не переписуються при перемиканні. Ручний вибір мережі не переходить
непомітно на інший профіль. HTTP 503 повторюється через іншу підтверджену
адресу, 401 / 403 мають різні пояснення. Передача списку перевіряє також
UUID відповіді та незмінність власника / ключа перед записом відповідностей.

Probe обмежено 1,5 с разом із DNS / відповіддю, 8 КБ, без редиректів,
cookies та proxy зі змінних середовища. Правила anti-SSRF збережені.
Профіль поточної адреси журналу переносить сталі порти / шляхи джерела.
Docker додає host-gateway та профіль «Цей сервер», що не залежить від LAN IP.
Bootstrap після міграцій не виконує мережевих запитів або передачі даних.

Перевірки: 659 повних тестів журналу та 19 остаточних тестів профілів OK;
29 однакових тестів school_sync OK у всіх трьох репозиторіях. Відтворено
зміну мережі, hostname, ручний режим, інший UUID / source, 401 / 403,
ліміти й передачу списку через нову адресу без зміни PK / оцінок.

Ручна перевірка на ізольованому стенді: GET ping без ключа повертає лише
три поля; вимкнути першу адресу й виконати передачу на другій, перевірити
незмінний ID прив'язки. З іншим UUID передача не починається. Інтерфейс
керування профілями додається на етапі 3. Старі клієнти v1 / v2 збережено;
для нових центральних профілів джерела оновлюються перед журналом.

## Етап 3 — одна сторінка підключень

Journal: owner-scoped «Підключення», мережеві профілі, картки статусу / прав /
UUID / версії / часу, майстер адреса → ключ → перевірка → готово, безпечна
заміна ключа. Старе меню ключів переходить у новий центр; налаштування
класу більше не просять адресу й токен. Порти задано профілем один раз,
збережені legacy-порти мають пріоритет. У конфігурації локального сервера
потрібні фактичні LOCAL_SCHOOLTEST_PORT / LOCAL_SCHOOLWORK_PORT.

SchoolTest / SchoolNet: довідка з UUID і готовими адресами, копіювання
працює також у LAN HTTP. Код підключення використовує поточну адресу
запиту. Ключ показується лише після створення. Необов'язковий Linux
compose.lan.yaml публікує лише LAN IP у tmpfs: worker без секретів, БД,
host-файлів, capabilities і Docker socket; застосунок читає том readonly.
За відсутності прав на інтерфейси сторінки продовжують працювати.

Цільові перевірки: ізоляція чужих сервісів / профілів / адрес, CSRF і POST,
повторне додавання, два джерела з одним host, відмова нового ключа без
втрати старого, відсутність ключів у DOM / JSON. 160 тестів SchoolTest і
74 API / key / roster / shared тестів SchoolNet пройшли. Повні остаточні
перевірки, браузер і встановлення виконуються після етапів 4–5.

Ручна перевірка на синтетичному стенді: додати обидва джерела в одну
мережу, перевірити картки; змінити мережу; спробувати неправильний ключ;
переконатися, що старі класи й оцінки залишилися. На джерелах скопіювати
поточну адресу та новий ключ і перезавантажити — ключ більше не показаний.

## Етап 4 — сталі класи та явні відповідності

Journal: матриця клас → SchoolTest → SchoolNet, окремий навчальний рік,
UUID класу журналу, UUID джерела та локальні ID. GET не робить HTTP.
Вибір класу перевіряється за свіжим roster; історія й відповідності
забороняють непомітне перепризначення. «Створити автоматично» викликає
чинний roster API, не створює новий контракт. Перейменування класу
з підтвердженим ID не вважається розривом прив’язки.

Учні: локальний пошук, показ ID, fuzzy ≥ 0.68 лише як підказка. Окрема
масова дія підтверджує тільки однозначні повні збіги після явної згоди.
Зміна локального / зовнішнього списку зупиняє застаріле підтвердження.
Окрема вкладка позакласних / alias лишилася; її масова дія також
перевіряє preview і не включає тезок або fuzzy.

Прибрано приховані автоматичні злиття за ПІБ у прийманні roster SchoolNet
і grades Journal. Старі підтверджені ID й оцінки збережено. Непідтверджені
імена залишаються позакласними до рішення вчителя. school_sync ідентичний
у трьох проєктах. SQLite: 683 повних тестів журналу OK; SchoolNet 75
цільових API / key / roster / shared тестів OK; SchoolTest 160 OK.

Ручна перевірка: відкрити «Зіставлення», оновити назви, зв’язати клас
за ID, перейменувати його на тестовому джерелі — ID лишається. Створити
двох тезок: масова дія їх не пов’язує. Змінити список між відкриттям
форми та підтвердженням — запис зупиняється без змін історії.

## Етап 5 — робота окремого журналу

У detail.html один sync_panel.html: для двох джерел окремі форми roster /
grades, видимий період, час, підсумки, зіставлення, конфлікти й позакласні.
Адреси / ключі не вводяться в журналі, включно з попереднім розширеним
інтерфейсом. Нестандартний v1 редагується за окремим центральним URL;
його форма та збережений ключ сумісні. Прямі старі API збережені.

Отримання оцінок більше не виконує прихований roster POST. Налаштування
журналу: увімкнення джерела, період 1–366 днів, урок за замовчуванням.
Чужий / підсумковий урок відхиляється. Default placement діє лише для
нових робіт без окремого вибору; пізні результати й наявна історія не
переміщуються. Ручна / погоджена оцінка захищена.

SQLite: 689 повних тестів Journal OK; 6 остаточних цільових перевірок
налаштувань OK. SchoolTest 160 OK; SchoolNet 17 фінальних key / API
перевірок OK, включно з поточним hostname замість PUBLIC_BASE_URL.
Підготовлено VERSION / код / Docker / CHANGELOG / RELEASES для
Journal 1.4.0, Test 1.7.0, Net 4.6.0. Це ще не підтвердження встановлення:
повні PostgreSQL, браузер, резервування й сервер перевіряються окремо.

Ручна перевірка: окремо натиснути «Передати учнів», потім «Забрати оцінки»;
переконатися, що GET grades не надсилає roster. Вибрати default lesson
для нової роботи, отримати результат, змінити default і повторити —
попередня оцінка та її урок залишаються. Перевірити обидва джерела
на широкому екрані й телефоні.

PostgreSQL перевірка заповненої історичної схеми виявила взаємодію DDL
та pending FK trigger events: Django створює частину індексів у кінці
schema_editor. Дані перенесено в окрему атомарну міграцію 0022 після
DDL 0020 / defaults 0021. Це зберігає атомарність перенесення й дозволяє
повний відкат до 0019 із відновленням старого ключа. Зміна перевіряється
на заповненій SQLite та PostgreSQL до встановлення на сервер.
