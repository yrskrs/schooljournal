# Взаємодія тестів, завдань і журналу

Усі три сайти рівноправні та працюють зі своїми постійними локальними даними. API має власний номер контракту, незалежний від версії сайту: schooltest5 **1.4.1**, schoolwork2 **4.3.0**, schooljournal **1.2.1** підтримують **v2**. Наявні API v1 збережені. Старий запис списків за ПІБ у schoolwork2 повертає 409 після приєднання класів до v2, щоб не втратити явні прив’язки. Непідтримувана версія v2 дає зрозумілу помилку; списки й оцінки не очищаються. Оновлюйте сайти окремо, увімкніть обмін v2 після оновлення учасників.

## Просте підключення до журналу

1. У тестах відкрийте **«Підключення до журналу»**, у завданнях — **«Налаштування → API та журнал»**. Натисніть **«Створити API для журналу»** та **«Скопіювати код підключення»**.
2. Відкрийте потрібний журнал і натисніть **«Підключити тести / завдання»**. Вставте код; за бажанням можна ввести адресу сайту й ключ окремо. Натисніть **«Підключити й отримати назви»**.
3. Оберіть клас і предмет **за назвою**. ID, маршрути API та поля JSON вводити не потрібно.
4. Перевірте таблицю учнів і підтвердіть відповідність. Збіг імен — лише підказка до підтвердження; різні учні з однаковими іменами не об’єднуються. Відсутнього учня можна явно додати як нового до цього класу. Історичні прив’язки вже імпортованих оцінок змінити не можна.
5. Надалі в журналі натискайте **«Синхронізувати з тестами»** або **«Синхронізувати із завданнями»** за потрібний період. Налаштування підключення та отримання назв не імпортують оцінок. Приймаються готові цілі 1–12; ручні оцінки збережені.

Назви джерела зберігаються у базі журналу; відкриття сторінки не звертається до іншого сайту. **«Оновити назви класів та учнів»** отримує новий список, не видаляє локальних учнів чи їхню історію та не імпортує оцінок. Помилка залишає попередній кеш. Це простий спосіб налаштувати отримання оцінок; рівноправний фоновий обмін місцевими списками описаний далі й не змінено.

У тестах після створення ключа назви класів і предметів готуються з даних власних тестів, без зміни сесій та способу входу учнів. Обов’язковий вибір учня зі списку вмикається лише після явного налаштування сесії вчителем. Сесії з чинним контекстом не переприв’язуються. Якщо назви відсутні, виберіть клас і предмет у розділі підготовки. Старі спроби без локального учня потребують явного вибору його імені; API не вгадує особу за ПІБ.

Для адміністратора: код підключення містить секретний ключ і передається лише у власний журнал. `PUBLIC_BASE_URL` задає браузерну адресу; `JOURNAL_API_BASE_URL` — доступну серверу журналу адресу для коду (наприклад `http://schooltest-api:8000` / `http://schoolwork-api:8000` у спільній Docker-мережі). Якщо адреса API окремо не задана, використовується браузерна адреса. Для різних Docker-хостів задайте доступний DNS/IP; `localhost` іншого контейнера не підходить. Нового зовнішнього маршруту журналу не потрібно.

Оновлення: `./scripts/update.sh` у тестах і завданнях; `./update.sh origin/main` у журналі. Код отримується з налаштованого GitHub-репозиторію через HTTPS, зберігаючи origin і допускаючи лише fast-forward. SSH-ключ GitHub для публічного репозиторію не потрібний; для приватного потрібен налаштований Git credential helper. Зберігаються резервні копії, правильні версії/ревізії образів і унікальні aliases; nginx журналу перезапускається після web. У тестах і завданнях старе `.env` перед зміною тега додатково зберігається як `.env.before-image-update`.

Міграція журналу `journals 0011` додає кеш назв і час отримання до підключень; існуючі записи не змінює. Перед міграцією потрібна резервна копія. Для відкату поверніть попередній образ та його конфігурацію, залишивши додані поля; накопичені дані не відновлюйте старим snapshot без окремого рішення.

## Розширені дії вчителя

1. На одному з сайтів приєднайте місцевий клас до обміну. Це лише початкова публікація ID, а не призначення головного сервісу. На інших сайтах явно зіставте спільний ID із місцевим класом. У журналі адміністратор спершу задає `ROSTER_SCHOOL_ID` і `ROSTER_YEAR_ID` у серверній конфігурації.
2. Кожного наявного учня зіставте за його місцевим ID. Однаковий ПІБ не об’єднує записи. Підтверджуйте створення нового учня лише якщо місцевого запису справді немає. Якщо клас приєднали незалежно у кількох сервісах, явне зіставлення передасть alias ID; місцеві PK та історія зберігаються.
3. Редагуйте дані у звичних засобах сайту; у тестах — «Списки». Нові учні в уже приєднаному класі отримують окремий UUID. Після початкового зіставлення такі учні можуть копіюватися автоматично, якщо немає незiставлених місцевих записів чи збігу імен. Збіг імен завжди потребує рішення, ніколи не означає тотожність.
4. У разі конфлікту перегляньте місцеву й отримані версії та явно оберіть потрібну. Рішення об’єднує відомі версії й поширюється у фоні. Якщо запис змінився після перегляду, оновіть сторінку. Однакові зміни полів можуть узгодитися без вибору, оскільки суперечності в даних немає. Два різні рішення вчителів, зроблені одночасно, знову потребують ручного вибору.
5. У тестах прив’яжіть власну сесію до місцевого класу, предмета та дати уроку; за потреби вкажіть номер уроку. Старі спроби явно зіставте з ID учня. Контекст уже прив’язаної сесії не можна перекинути на інший клас/предмет: створіть нову сесію. У завданнях використовуються чинні `Assignment.classes` та предмет завдання.
6. Створіть окремий ключ експорту оцінок: тести — «Підключення до журналу» (код показано один раз; новий код не вимикає інших журналів; явне відкликання доступне в розширеному розділі); завдання — «Налаштування → API та журнал» (дозвіл експорту). У журналі в «Профілі та API» створіть підключення відповідного джерела, виберіть контракт **v2**, введіть URL для сервера, ключ та **ID класу й предмета на сайті джерела**. Явно зіставте ID учнів джерела з учнями поточного журналу. Списки native-ID для налаштування доступні серверним GET `/api/v2/journal/roster/` із ключем експорту.
7. У журналі виберіть період (місяць/семестр/рік), натисніть **«Синхронізувати з тестами»** або **«Синхронізувати із завданнями»**. Перша кнопка опитує лише тести, друга — лише завдання. Сервер перевіряє право редагувати цей журнал, джерело, клас, предмет, період і належність учня. Для оцінки має існувати однозначний урок на дату (або дата + номер уроку).

Фоновий обмін переносить **лише списки**. Запуск, перегляд сторінок та GET API не імпортують оцінок. Джерела зберігають результати, доки журнал недоступний; наступна дія вчителя за потрібний період повторно отримує всі поточні результати, включно з виправленнями. Повторна спроба тесту замінює результат відповідної сесії й учня; повторна здача завдання — результат завдання, класу й учня. Нова неостаточна спроба не повертає стару як нову остаточну, і вже імпортована оцінка не видаляється автоматично. Окремі сесії тесту мають окремі ID результатів.

Імпортуються лише готові цілі **1–12 зі шкали 12**. У тестах зберігається чинне `round(score / max_score * max_grade)`, без нового перерахунку: 0 та інші шкали потребують ручного рішення. У завданнях передається оцінка вчителя; дробові, рівневі й інші значення також потребують ручного рішення. ШІ-пропозиція без підтвердження вчителем не остаточна.

**Додано / оновлено** — кількість записаних оцінок; **без змін** — отриманий результат уже є; **конфлікт** — клітинка зайнята ручною оцінкою, відвідуванням або захищеним рішенням учителя; **помилка** — незiставлений ID, неготове значення, відсутній урок чи неправильний контекст. Деталі видно у «Оцінки з робіт». Виправлення можуть оновити тільки власну імпортовану оцінку; будь-яке ручне редагування клітинки передає її вчителю. Зайняту клітинку можна замінити лише явним рішенням у перегляді конфлікту.

**Узгоджено / ready** — поточна локальна версія; **потрібне зіставлення / unmapped** — потрібне рішення за ID; **conflict** — одночасні суперечливі зміни. У підказці статусу відрізняються успішна порожня відповідь, HTTP-помилка, несумісність та недоступність. Порожня відповідь і відсутність запису в snapshot не означають видалення. Явне `active=false` означає зняття зі списку без видалення PK чи історії. У завданнях кнопка видалення учня знімає активність; у журналі закривається зарахування в клас зі збереженням журналів.

## Адреси, мережа та ключі адміністратора

| Сервіс | Сайт для браузера на цьому хості | HTTP API між контейнерами |
|---|---|---|
| schooltest5 | `http://HOST:8080` | `http://schooltest-api:8000` |
| schoolwork2 | `http://HOST:8000` | `http://schoolwork-api:8000` |
| schooljournal | `http://HOST:8085` | `http://schooljournal-api:8000` |

Наведені браузерні порти відповідають цьому розгортанню та новим типовим значенням. БД тестів використовує host 5432, завдань — 5433; БД журналу не публікується. `APP_PORT`, `WEB_PORT`, `WEB_BIND`, `DB_PORT`, імена Compose та URL залишаються налаштовуваними. Фактичні `.env` не публікуються. Журнал має власний nginx; його маршрути не перетинаються з прямими портами інших сайтів. Домени зовнішнього reverse proxy задає адміністратор окремо.

Для одного Docker-хоста створіть bridge `docker network create school-integration` один раз. Скопіюйте **опціональний** `compose.integration.yaml` у локальний **непублікований** `compose.override.yaml`. Він додає вебсервіси та чинний worker завдань до зовнішньої мережі з унікальними aliases, зберігаючи приватні мережі й постійні томи. БД інших проєктів у спільній мережі немає. Назви Compose-проєктів — schooltest5, schoolwork2, schooljournal; на одному хості має бути лише один власник кожного alias. Для іншої трійки використовуйте іншу `INTEGRATION_NETWORK`. Середовище журналу враховує override також через `scripts/common.sh` під час оновлення/backup.

У серверному `.env` кожного сервісу:

```dotenv
INTEGRATION_NETWORK=school-integration
ROSTER_SYNC_TOKEN=replace-with-a-separate-random-long-server-token
ROSTER_PEERS=[{"url":"http://OTHER-ALIAS:8000/api/v2/roster-sync/","token":"the-other-server-token"}]
ROSTER_SYNC_INTERVAL=30
```

Задайте **два інших** peers кожному учаснику, власний токен — окремий. Інтервал щонайменше 2 секунди; повторні спроби із затримкою до 300 секунд. Штатний запит має timeout 6 секунд; помилка не блокує вебзапуск чи локальні сценарії. У журналі `ROSTER_SCHOOL_ID=0` / `ROSTER_YEAR_ID=0` вимикають область обміну: задайте точні місцеві ID школи й року. Спільні записи публікуються лише після явного приєднання класу вчителем. Ключ API списків адміністративний; ключі оцінок відокремлені. Ключ вчителя завдань у v2 завжди обмежений його завданнями; глобальний ключ без власника призначений адміністратору. У тестах кожен ключ завжди належить учителю.

Для різних Docker-хостів bridge не дає зв’язку. Замініть URL на доступний серверу журналу/джерелу DNS/IP з чинним маршрутом, firewall та HTTPS або захищеною приватною мережею. Для peer-обміну списками кожен сервер має досягати налаштованих інших серверів; для оцінок достатньо вихідного зв’язку **журнал → джерело**. `localhost` всередині контейнера належить самому контейнеру, не іншому сайту. Перенаправлення URL та loopback/link-local адреси для нового обміну відхиляються. Відкриття локального журналу назовні цими змінами не виконується; таку зміну інфраструктури погоджуйте окремо.

Браузер працює з власним сайтом. Server-to-server запитам CORS не потрібен; permissive CORS не додається. Учительські POST захищені cookie-авторизацією та CSRF. Не додавайте ключі у JS, HTML загальнодоступних сторінок, query-параметри чи Git. Налаштуйте allowed hosts / CSRF origins журналу за його чинною інструкцією; зміна адреси не потребує редагування Python.

## Контракт v2

`GET /api/v2/roster-sync/`, тільки `Authorization: Bearer SERVER_TOKEN`, повертає:

```json
{"schema_version":2,"origin":"instance-UUID","records":[
 {"ref":"class-UUID","kind":"class","payload":{"name":"7-А","grade_level":7,"letter":"А","active":true},"clock":{"instance-UUID":1}},
 {"ref":"student-UUID","kind":"student","payload":{"name":"Вигаданий Учень","first_name":"Учень","last_name":"Вигаданий","middle_name":"","class_ref":"class-UUID","active":true},"clock":{"instance-UUID":1}}
]}
```

`instance-UUID`, `class-UUID`, `student-UUID` у прикладі — замінники справжніх UUID. `ref` стабільний; локальні numeric PK не перезаписуються. Явне зіставлення двох раніше створених UUID передається як `kind=alias`, `payload={"target":"canonical-UUID"}`. Вектор `clock` визначає старішу/новішу/одночасну версію без залежності від годинників хостів. `RosterReplica` зберігає local PK, конфліктні пропозиції та статус; `RosterState` — identity, очікувані початкові зіставлення, стан retries та останні рішення. Ідентичність сервісу не можна клонувати копіюванням його БД для нового peer. Зміна відомого origin або дублі alias/peers потребує виправлення конфігурації.

Місцеві редагування native-моделей та отримання змін використовують одне DB-блокування, щоб обмін не затер незахоплену місцеву зміну. Snapshot максимум 50 000 записів / 8 МБ, до 16 origin у clock і 16 невирішених пропозицій одного запису. Помилка валідації відкатує транзакцію отримання. Snapshot отримується поза локальною DB-транзакцією; native-зміни й metadata фіксуються разом. Фоновий обмін використовує чинні web workers тестів/журналу та AI worker завдань; нового мережевого сервісу немає. `school_sync/` — однаковий vendored протокол; змінюйте й перевіряйте його узгоджено в трьох репозиторіях.

`GET /api/v2/journal/grades/?class_id=ID&subject_id=ID&date_from=YYYY-MM-DD&date_to=YYYY-MM-DD&cursor=0`, тільки `Authorization: Bearer GRADE_EXPORT_TOKEN`, повертає:

```json
{"schema_version":2,"source":"schooltest","grades":[
 {"source":"schooltest","id":"schooltest:session:5:student:41","student_id":41,"class_id":7,"subject_id":3,"work_id":9,"title":"Вигаданий тест","attempt_id":12,"points":8,"max_points":12,"value":"8","grading_scale":12,"date":"2026-09-05","lesson_number":1,"status":"final","updated_at":"2026-10-10T12:00:00+03:00","is_ai":false,"approved_by_teacher":true}
],"next_cursor":null}
```

Для завдань `source=schoolwork`, ID `schoolwork:assignment:A:class:C:student:S`; для тестів ID `schooltest:session:T:student:S`. Учні без явного native FK повертаються з `student_id=null` і окремим ID unmapped; журнал показує потребу ручного зіставлення, не шукає ПІБ. `updated_at` містить часовий пояс; журнал не застосовує старішу ревізію. `lesson_number` необов’язковий. Бали завдання дорівнюють його числовій оцінці зі шкали 12; для нечислових чи позашкальних значень технічне `points=0`, але оригінальне `value` збережено й потребує ручного рішення. Сирих балів завдань наявна модель не має.

Сторінка має до 500 результатів; `next_cursor` — числовий cursor наступного GET або `null`. Журнал отримує весь період до запису, не лише нові результати, максимум 100 сторінок / 50 000 оцінок, до 2 МБ на сторінку. Якщо сторінка недоступна, має неправильну версію чи cursor, цей імпорт не починається. За надто великого періоду звузьте його. Джерело обмежує обробку 100 000 спроб у контексті. `GET /api/v2/journal/roster/` повертає native IDs класів, предметів та учнів для ручного налаштування, не виконує синхронізацію.

## Оновлення та відкат

Перед оновленням збережіть образ із поточного `docker inspect`, конфігурацію `.env` / Compose, узгоджену резервну копію PostgreSQL і медіа за чинною інструкцією проєкту. Перевірте `pg_restore --list` і контрольні суми архівів. Не видаляйте томи. Для schooltest5 застосовується наявний ідемпотентний startup-upgrade: нові таблиці та nullable FK/час оновлення, старі спроби залишаються без прив’язки. У schoolwork2 міграція 0057 додає metadata/active/по батькові та знімає обмеження унікальності ПІБ, щоб різні учні могли мати однакові імена. У schooljournal — curriculum 0004, journals 0009/0010, без видалення оцінок або зарахувань. Міграція accounts 0004 з випуску 1.0.1 лишається.

Перезберіть власний version-tagged образ і виконайте `docker compose up -d --wait` (журнал: чинний `scripts`/`dc` із `.release-image.yaml` та override). Сайт завдань і його AI worker мають використовувати один новий образ. Перевірте версію сайту й OCI label, healthcheck, запуск без traceback, auth API, кількість наявних записів і доступ до завантажених файлів. Після перестворення контейнерів виконайте `python3 scripts/configure_integration_network.py`: Compose додає типовий alias `app`, який може збігатися у двох проєктів; ця команда залишає в спільній мережі лише явно налаштовані унікальні aliases і перевіряє відсутність дублювання. Приватні мережі й порти не змінюються. Звичайний restart зберігає налаштування aliases. Зробіть restart і повторіть перевірку даних. Не запускайте `down -v`, `volume rm` або глобальне очищення Docker.

Для швидкого відкату зупиніть записи, збережіть **нову** резервну копію після оновлення, вимкніть peers і підставте збережений попередній образ та конфігурацію. Адитивні колонки можна залишити; метадані API v2 попередній код не читає. У schoolwork2 за появи двох однакових ПІБ попередній код не гарантує правильну роботу: потрібне повернення узгодженої резервної копії БД і медіа або виправлення перед відкатом. Повне повернення БД до snapshot потребує окремого рішення щодо даних, накопичених після backup; не відновлюйте стару БД автоматично. Reverse migrations, що видаляють integration metadata, не використовуйте як спосіб відкату. Після повернення образу перевірте версію, health і дані.

## Перевірки

Спільні сценарії протоколу: `python -m unittest school_sync.tests.test_protocol`. Тести працюють лише з вигаданими даними. Повний сценарій трьох образів, PostgreSQL, HTTP-кнопок, відсутності зв’язку та restart запускається в окремому Compose-проєкті `tests/integration/` у репозиторії schooljournal. Звіт фактично виконаних перевірок: `INTEGRATION_CHECKS.md`. Цей контракт не стверджує доступність зовнішніх хостів чи роботу неперевірених reverse proxy.

## Дозволений хост внутрішнього API журналу

У `.env` журналу включіть `web,schooljournal-api` до `ALLOWED_HOSTS` поряд із браузерною IP-адресою чи доменом. Django перевіряє Host також для серверних API-запитів: правильний ключ не усуває HTTP 400 від відсутнього API alias. Після зміни `.env` перестворіть web, налаштуйте унікальні aliases командою `python3 scripts/configure_integration_network.py` та перезапустіть nginx. CSRF_TRUSTED_ORIGINS задає браузерні адреси; ключі для API передаються лише між серверами.
