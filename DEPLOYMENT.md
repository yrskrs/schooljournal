# Сервер, оновлення та відновлення

## Перше розгортання

1. Встановіть Docker Engine, Compose v2, Git, Python 3.12+, Bash та util-linux. Дайте адміністратору сервера доступ до Docker.
2. Клонуйте main через HTTPS: git clone --branch main https://github.com/yrskrs/schooljournal.git. Запустіть ./setup.sh і налаштуйте .env за README.
3. Виконайте docker compose config --quiet, потім docker compose up -d --build --wait --wait-timeout 180.
4. Відкрийте адресу сервісу у браузері. На першому вході з’явиться форма «Створити суперадміністратора». Введіть INITIAL_SETUP_TOKEN із .env, логін, email та пароль двічі. Після створення відкриється кабінет і форма налаштування більше не буде доступна. Якщо адміністратор уже існує, цей крок пропускається автоматично.
5. Перевірте /healthz/, вхід, реєстрацію, /help/ та /versions/.
6. Зареєструйте школу й налаштуйте класи та вчителів або увійдіть через nz.ua та імпортуйте особистий журнал.

PostgreSQL не має зовнішнього порту. Дані зберігаються в named volumes. docker compose down зберігає їх; down -v видаляє дані, тому його не використовуйте для оновлень.

Не змінюйте POSTGRES_USER, POSTGRES_DB та POSTGRES_PASSWORD після ініціалізації PostgreSQL без окремого переналаштування бази. Зміна .env не змінює пароль уже створеної бази.

## Наявний локальний сервіс

Для переходу з release/v1.0.0 на main у чистому Git checkout виконайте `./update.sh origin/main`. Скрипт збере образ, створить резервну копію та застосує міграції. Після успішного оновлення виконайте `git branch -m main` і `git branch --set-upstream-to=origin/main main`, якщо локальна гілка ще називається release/v1.0.0.

Якщо у наявному сервісі немає суперадміністратора й коду INITIAL_SETUP_TOKEN, після оновлення виконайте `./setup.sh` та `./service.sh up -d --force-recreate web`. Скрипт додає код, зберігаючи SECRET_KEY і пароль PostgreSQL. Коли суперадміністратор уже є, міграція закриває початкове налаштування. Автоматичне створення адміністратора в entrypoint через FIRST_SUPERADMIN_* вилучено.

Якщо переходите з папки без Git на підготовлений клон, спершу збережіть базу, media й чинний .env. Скопіюйте цей .env у клон, зберігши SECRET_KEY, параметри PostgreSQL та ім’я Compose-проєкту. Не генеруйте новий пароль для вже наявного volume PostgreSQL.

Вимкніть SEED_DEMO_DATA для робочої бази. Імена named volumes мають збігатися з попереднім розгортанням. Запуск нового Compose з тим самим COMPOSE_PROJECT_NAME використовує ці дані; не виконуйте down -v. Надалі керуйте сервісом з одного канонічного Git checkout та використовуйте update.sh.

## HTTPS і зовнішній проксі

Nginx у Compose обслуговує HTTP. Для публічного сервера поставте TLS-проксі з сертифікатом перед ним. При проксі на цьому ж сервері задайте WEB_BIND=127.0.0.1.

Зовнішній проксі має передавати початковий Host. Для повідомлення Django про HTTPS змініть у nginx/nginx.conf директиву:

~~~nginx
proxy_set_header X-Forwarded-Proto https;
~~~

Це підходить лише коли весь клієнтський доступ проходить через HTTPS-проксі, HTTP перенаправляється в HTTPS, а прямий порт Compose закритий. Встановіть CSRF_TRUSTED_ORIGINS=https://journal.example.org, додайте домен до ALLOWED_HOSTS і увімкніть secure cookies. SECURE_SSL_REDIRECT=True вмикайте після правильного налаштування протоколу.

Комітьте конфігурацію проксі або зберігайте її як контрольовану конфігурацію розгортання: update.sh відмовляється працювати з незбереженими змінами коду. Перевірте конфігурацію командою docker compose exec web python manage.py check --deploy. Налаштування HSTS залежить від вашого домену й завершеного HTTPS.

## Оновлення

Версія 1.3.33 відновлює права читання 0644 тільки для публічних VERSION, RELEASES.json і CHANGELOG.md після Git-оновлення та перед перевіркою запуску. `.env` та резервні копії залишаються приватними. Перед зупинкою сервісу перевіряється можливість заміни тек коду під час відкату; теки іншого власника спочатку потрібно виправити адміністратору сервера.

Для першого CLI-переходу зі старого оновлювача (до 1.3.33) запускайте нові скрипти з тимчасового каталогу, щоб вони діяли вже під час цього оновлення. Із чистого канонічного checkout:

```bash
git fetch origin main
UPDATER_TOOLS=$(mktemp -d /tmp/schooljournal-updater.XXXXXX)
git archive origin/main scripts | tar -x -C "$UPDATER_TOOLS"
JOURNAL_ROOT="$PWD" bash "$UPDATER_TOOLS/scripts/update.sh" origin/main
rm -rf -- "$UPDATER_TOOLS"
```

Цей запуск збирає опубліковану ревізію й створює штатну резервну копію до зміни checkout. Надалі використовуйте звичайний `./update.sh` або сторінку «Оновлення системи».

Передумови: сервіс працює, Git checkout чистий, origin доступний, вистачає диска для двох образів, архіву та його тимчасової розпаковки. .env, media, backups і .release-image.yaml ігноруються Git.

~~~bash
./update.sh origin/main
~~~

Поки збирається новий image, поточний сервіс працює. На створення узгодженої копії й міграції доступ тимчасово зупиняється. Скрипт залишає старі images; не очищайте їх під час оновлення. Архів містить image, тому можливе відновлення після локального очищення.

За успіху перевірте версію на сайті. За невдачі повертається ненульовий код; автоматичне відновлення повертає стан до оновлення. Якщо воно теж не вдалося, використайте вказаний архів вручну. Помилки відновлення не приховуються.

ENV_FILE=/absolute/path/.env ./update.sh origin/main задає інший файл середовища. Це працює також для backup/restore. COMPOSE_PROJECT_NAME має збігатися з чинним розгортанням. Типовий timeout перевірки — 180 секунд.

## Копія та відновлення

~~~bash
./backup.sh
./restore.sh --check backups/schooljournal-ДАТА.tar.gz
./restore.sh backups/schooljournal-ДАТА.tar.gz --yes
~~~

Архів містить database.dump, media.tar.gz, source.tar.gz, web-image.tar.gz, manifest.json та SHA256SUMS. Перевірка відхиляє неправильні суми, небезпечні шляхи, символьні посилання й невідомий формат. PostgreSQL-відновлення виконується в порожню тимчасову базу з припиненням на першій помилці, після чого імена баз перемикаються в одній транзакції. Це прибирає також таблиці, додані невдалим оновленням.

Відновлення точно замінює media; зайві файли видаляються. Код повертається до версії з архіву; за наявності відповідного commit локальна Git-гілка теж повертається до нього. Тому потрібний явний прапорець --yes. Спершу створюється safety backup. Внутрішній --no-safety-backup потрібний автоматичному відкату.

.env не входить у архів. Зберігайте SECRET_KEY та пароль бази окремо. Заміна SECRET_KEY скасує підписані локальні сесії; не міняйте його довільно при перенесенні.

## Інший сервер

1. Підготуйте Docker і клон репозиторію. Скопіюйте захищений .env та власний архів; уточніть хост і CSRF.
2. Запустіть базу: docker compose up -d --wait db.
3. Створіть web-контейнер: docker compose build web && docker compose create web.
4. На новій порожній базі виконайте ./restore.sh ARCHIVE --yes --no-safety-backup. Image, база, media та код завантажаться з архіву.
5. Перевірте версію, вхід, учнів і журнали. Сесії nz.ua можуть вимагати повторного підтвердження.
6. Створіть нову копію та збережіть її поза сервером.

## Діагностика

~~~bash
./service.sh ps
./service.sh logs --tail=100 web nginx db
curl --fail http://127.0.0.1:8085/healthz/
~~~

service.sh автоматично враховує .release-image.yaml. Для ручних Compose-команд після update/restore додавайте -f compose.yaml -f .release-image.yaml, якщо цей файл існує.

/healthz/ перевіряє Django й PostgreSQL та повертає версію. Відповідь Nginx без працюючої бази не вважається справним сервісом.

Не надсилайте .env, ключі, Cookies, dumps чи сторінки з даними учнів у GitHub або публічні логи. Репозиторій містить код і синтетичні тестові дані.
